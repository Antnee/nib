| 46 | Deferred cleanup | agreed | `defer expr` runs when the enclosing **block** exits (LIFO, Swift/Zig scoping, not Go's function scope). It runs on normal exit and on `fail`, but not on panic, where the host cleans up. A deferred call that can fail must handle its error. `defer else expr` runs only when the block exits via `fail` or `?` (Zig `errdefer`). Round 60 (#196): `defer else` runs when the block doesn't finish normally: on `fail`, `?`, and cancellation. It still doesn't run on panic. Cold read 29 found that `else` now has three jobs (after `if`, in a signature, and in `defer else`) and suggested a word of its own, such as `defer onFailure`. The user kept `defer else`. |

| 48 | Loops | agreed | `for x in iterable`, `while cond`, `while true`, and `do { … } while cond`. No C-style `for`. `break` / `continue` with arbitrary labels (`name: for …`, `break name`). The loop variable is immutable; collections are iterated as a snapshot. |
| 48a | Ranges | agreed | `1..10` inclusive, `0..<n` exclusive. `..=` is rejected entirely (one way to write it). Ranges are values. |
| 48b | Assignment | agreed | A statement, never an expression. Compound forms on `var`. `x++` / `x--` are postfix statements only, never expressions (as in Go). Lint autofix: `x = x + 1` becomes `x += 1`, and `x += 1` becomes `x++`. |
| 49 | Conditional expression | agreed | Ternary `cond ? a : b`. Nested ternaries need parentheses (as in PHP 8). No `?:` (there is no truthiness): use `??` for null, and `ifEmpty(default)` on strings and collections. `if … then … else` is rejected. Depends on #52. Note (cold read 18): the `?:` part is superseded by #53, which defines `?:` for `Emptiable` types. |
| 50 | `match` | agreed | Exhaustive. `_` is allowed as a default. A lint (on by default) warns when `_` covers variants of an enum from your own package. Alternatives use `or`. Guards use `if`. |
| 51 | Stdlib getter convention | agreed | Zero-argument, infallible, amortised O(1) members are getters (`list.length`, `list.isEmpty`). `String.length` gets an O(1) ASCII fast path (a flag set during UTF-8 validation) and a grapheme count computed lazily and cached on first read. |
| 52 | Propagation syntax | agreed | Replace postfix `?` with prefix `try` (Swift / Zig): `let order = try findOrder(db, id)`. This frees `?` for the ternary and removes the clash between `x()?.y` (propagate then access) and `?.` (null-safe access). `try` has no `catch`; failures are handled with `let … else` / `match`. Supersedes `?` in #9 if agreed. |
| 52a | Scope of `try` | agreed | Covers the whole expression to its right, including `Result` values. Parentheses can narrow it. It is a compile error if it covers nothing fallible. Not for `T?`. |
| 52b | Error conversion | agreed | `Cart(from CartError)`: a single unnamed payload marked `from`. `try` wraps a `CartError` into it automatically. Compile error if no variant, or more than one, accepts the type. `from` variants expose `.cause` for error chains. Otherwise use `.mapError(…)`. Cold read 18: Fable called the wrap at every `try` and `fail err` a hidden rule ("Rust's `?` plus `From`"), and warned that an agent can make a `try` compile by adding a variant, turning a user-facing outcome into a 500. Kept: the wrap shows in the signature and the enum, and it saves a wrapper on every call that can fail. Guide 06 now says what the line doesn't show, and to handle failures a caller tells apart with `else` before they're wrapped. Cold read 21: still the top item for both readers. Kept again, and the web layer narrowed instead: the shop's `WebError` now holds only failures a visitor can do nothing about, plus a guard's `SignInRequired`; an access refusal, which `try` had silently made a 404, is handled where it happens. Guide 14 says to keep a web error enum that way. Cold read 22 will show whether that's enough. |
| 53 | Elvis `?:` | agreed | Reopened. Cold read 25 (Sonnet) found `?:` too close to the ternary; the user kept both, since a PHP developer knows both and Nib's `?:` differs from PHP's only for `"0"`. `a ?: b` is defined only for types that implement `Emptiable` (String, collections): it means `a.isEmpty ? b : a`. Not for Bool or numbers (0 is not "empty"). It would replace `ifEmpty`. `??` stays for null. |
| 9g | `let … else` on nullable | agreed | `let user = findUser(id) else { return … }`. There is no error to bind, so there is no binding. |
| 54 | Naming case | agreed | Enforced by the compiler. PascalCase: types and enum variants. camelCase: functions, methods, fields, getters, variables, parameters. UPPER_SNAKE: `const`, at top level or inside a type (#185). lowercase dotted: modules. Acronyms as words: `HttpClient`, `userId`. Case only restricts names; it never changes meaning (unlike Go). |
| 55 | Static access | agreed | `Type.function()` / `Type.Variant`. Instances use `value.method()`. Because case is enforced, a capital letter before the dot always means a type. |
| 56 | Conversions | agreed | Each conversion is defined once, by its owner. Built-in conversions are `x.toY()`, and the return type shows whether it can fail: `small.toInt64() -> Int64`, `big.toInt8() -> Int8?`, `"42".toInt() -> Int else ParseError`. Domain types are built by their own constructors (`Email.parse(raw)`). `Y.from(x)` is dropped, which leaves `from` meaning only error wrapping. Round 64: `Int64` is dropped (#231), so there is no `toInt64()`. |
| 57 | Opt-in truthiness (`Boolable`) | rejected | The call site cannot show which question is being asked. Use a named getter (`decision.isAllowed`). |
| 58 | Form / query decoding | agreed | Request input is decoded into records (`Form.decode<T>(req)`). The form codec documents its Bool rules (`"1"`, `"true"`, `"on"` vs `"0"`, `"false"`; a missing checkbox takes the field default). Failures produce per-field `DecodeError`s, which suit a 422 response. Every field type must be form-decodable (a built-in scalar, a backed enum, a `Parseable` type, `T?`, or `List<T>` of these), checked at compile time (#75). |
| 59 | Comments | agreed; amended by #243 | `//` line comments, plus nestable `/* … */` (so part of a line can be commented out, and code that already contains comments can be commented out). `#!` shebang on the first line only. `///` CommonMark doc comments, whose examples are compiled and run as tests. Comments never affect compilation. Amended by #243: doc-comment examples are parsed, not run. |
| 60 | Interfaces | agreed | They are types, so they are PascalCase. No `I` prefix and no `Interface` suffix. Implementations are named for what they are (`StripeGateway implements PaymentGateway`). |
| 61 | Error types | agreed | There is no special error kind. Anything can be the `else` type. An optional `Error` interface provides `message` / `.cause` for logging. Round 64: superseded in part by #236, so every `else` type now implements `Error`. |
| 62 | Testing | agreed | Built in (`nib test`). `test "name" { … }` blocks in `x.test.nibl` files beside the source, in the same package. `expect <bool expr>` with power-assert output. Test bodies may use `try`, and an error fails the test with its error chain. `expect x is Err(…)` for failures; `expectPanic` for panics. Setup is plain function calls; teardown is `defer`. Data providers: `test "…" for (a, b) in [...]`, with each row reported separately. Fakes are interface implementations, including inline anonymous ones; there is no reflection mocking. Each test runs in its own instance, in parallel by default. `--json` output. |
| 62a | Anonymous implementations | agreed (spelling changed by #167) | `let g = new PaymentGateway { fn charge(…) -> … { … } }` builds a value implementing an interface inline. Used mainly in tests. |
| 62b | Time and randomness | agreed | Use the injected `Clock` / `Random` interfaces, so tests can swap them (`FakeClock`). Belongs in the design-patterns round. |
| 28a | `_` member shorthand | superseded by #160 (now `.total`) | Was: `_.total` means `fn(x) => x.total`, and `_.total.isPositive` chains. `_` is allowed as the receiver of a member chain or as a call argument (#28), never as an operand (`_ > 3` is invalid). The placeholder expression extends to the enclosing argument. |
| 63 | Closure capture | agreed | Captures automatically, by value, read-only. `use (mut x)` captures a `var` by reference so the closure can mutate it. `use` only accepts `mut`; a plain `use (x)` is a compile error ("already captured"). |
| 64 | Fallible closures | agreed | `return` / `try` / `fail` inside a closure leave only the closure. Higher-order functions are generic over the error type: `fn map<U, E>(f: fn(T) -> U else E) -> List<U> else E`. With an infallible closure, `E` is `Never` and `else Never` disappears, so `try orders.map(fn(o) => try quote(o))` works with no `tryMap` variant (Swift `rethrows`). |
| 65 | Pipe operator | agreed | `x \|> f` passes `x` to a one-argument callable: a bare single-arity function, or a closure (`x \|> fn(v) => clamp(v, 0, 10)`; placeholder partial application was dropped by #160). The value is never inserted implicitly (unlike Elixir). Works with `try` across the whole chain. |
| 66 | Callables | agreed | Functions are values with types `fn(A) -> B else E`. Callables are: named functions, static functions (`Name.parse`), partial applications, closures, and bound non-mut methods (`formatter.format`). A bound `mut fn` needs a closure with `use (mut x)`. No string or array callables, and no invokable objects (`__invoke`); use an interface instead. |
| 66a | Invokable objects (`__invoke`) | rejected | An object that pretends to be a function hides what it is. Use an interface with a named method. |
| 66b | Bound `mut` methods as callables | rejected | `button.onClick(counter.increment)` would hide a mutation. Write `fn() use (mut counter) => counter.increment()`. |
| 67 | Uniform function call syntax (UFCS) | rejected | Calling any function as if it were a method (`x.f()` for `f(x)`, as in D and Nim) means `x.f()` no longer tells you where `f` lives. Methods come from the type; free functions chain with `\|>`. |
| 68 | Generics syntax | agreed | Angle brackets: `List<T>`, `fn first<T>(items: List<T>) -> T?`, `record Page<T> { … }`, `enum Tree<T> { … }`. Type arguments are inferred where possible and written explicitly otherwise (`Form.decode<SignupForm>(req)`). Made unambiguous by #72. No higher-kinded types, specialisation or const generics in v1. |
| 68a | Type argument inference | agreed | Type arguments are inferred from the call's arguments only, never from the expected return type. If a type parameter appears only in the return type, you write it: `Form.decode<SignupForm>(req)`. The target type is always visible at the call. |
| 68b | Higher-kinded types | rejected | Abstracting over type constructors (`F<_>`, so one `map` works for List, Result, Task). Costs: much harder inference, worse errors, and a pull towards abstraction for its own sake. Adding them later is backwards compatible. |
| 68c | Specialisation | agreed | User-visible specialisation (a different implementation, and so possibly different behaviour, for one type argument, as in C++'s `vector<bool>`) is rejected. The compiler may specialise for speed, as long as it can't be observed. Round 17: overlapping specialisations would be a compile error anyway, but the real hazard is behaviour that changes with the type, and overlap rules don't prevent that. |
| 68d | Const generics | agreed (reserved) | Values as type parameters (`Matrix<3, 3>`, `Bytes<32>`). The syntax `<const N: Int>` is reserved, so they can be added later. If added, start with Rust's minimal form: integer parameters, no arithmetic on them. |
| 69 | Generic constraints | agreed | Inline only: `<T: Comparable>`, combined with `and` (`<K: Hashable and Comparable>`). No `where` clause (one way). Constraints are interfaces. `This` (PascalCase) names the implementing type inside an interface. |
| 69a | Retroactive conformance | rejected | `implements` appears only on the type's own declaration. To make someone else's type fit your interface, wrap it in a distinct type or an adapter. Same reasoning as #67: you can always see where behaviour comes from. |
| 69b | Generics at runtime and performance | agreed | Semantics: type arguments are not erased. Strategy (as in C#/.NET): specialise once per value-type layout (Int, Float, Decimal, records) and share one copy across reference types (classes, interfaces), which all look like a pointer. Spec guarantee: a generic container of a value type never boxes its elements (`List<Int>` is a flat array of i64). The dev VM may share more code to compile faster; release and WASM builds follow the rule. |
| 70 | Operator overloading | agreed: not in v1; amended by #252 | Operators are defined only for built-in types (numbers, Decimal, Duration/Instant; #252 narrowed this to numbers). User types use named methods (`a.add(b)`). The C#-style design (operators declared in the type body, a fixed set, one operand must be the declaring type) is recorded here in case a real need, such as vector maths, comes up through the evolution process. Adding it later is backwards compatible; removing it would not be. |
| 70a | Operators on distinct types | replaced by #334 | A distinct type has no operators of its own. Arithmetic widens to the base and yields the base type (`cents + 1` is an `Int`). Replaced by #334: a distinct type has arithmetic only if it implements `Numeric`. |
| 71 | Equality and ordering | agreed | Records, enums and distinct types get structural equality automatically. Classes have no equality unless they implement `Equatable` (`fn equals(other: This) -> Bool`). Ordering is opt-in only, through `Comparable` (`fn compare(other: This) -> Ordering`), which provides `< <= > >=`, sorting, `min` and `max`. Identity is checked with a named function (`sameInstance(a, b)`), never an operator. Open: whether you write `a == b` only, or `a.equals(b)` as well. Round 17: `==` is the one spelling. `equals` is the method behind it for `Equatable` classes, and a lint autofixes `a.equals(b)` to `a == b`. |
| 72 | Chained comparisons | agreed | `a < b < c` is a compile error (suggest `a < b and b < c`, or `b in a..c`). This also keeps `f<T>(x)` unambiguous. |
| 73 | Conditional methods | agreed | A method of a generic type can require more of its type parameter: `pub fn contains(item: T) -> Bool when T: Equatable`, `pub fn sum() -> T when T: Numeric`, `pub fn sorted() -> List<T> when T: Comparable`. Calling one when the constraint isn't met is a compile error that names the constraint. |
| 74 | Static interface members | agreed (example updated by #169) | Interfaces can require static functions: `interface Parseable { static fn parse(text: String) -> This else Error }`. Generic code calls them on the type parameter (`T.parse(text)`). |
| 75 | `Parseable` | agreed (refined by #169) | Standard interface for "can be built from text". Implemented by built-in scalars and backed enums (via their backing values) and opted into by user types (`type Email = private String implements Parseable`).
